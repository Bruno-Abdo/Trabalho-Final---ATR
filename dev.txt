> **Papel:**

>

## 1. Contexto e Reenquadramento

> **Onde esta tarefa se encaixa:**
> No sistema de controle do caminhão autônomo, a tarefa **Tratamento Sensores**:
>
> * lê as medições de posição, ângulo e demais sensores;
> * aplica um **filtro de média móvel** de ordem M nas medições (especialmente posição/ângulo/temperatura); 
> * grava as amostras **tratadas** em um **buffer circular compartilhado** para serem consumidas pelas demais tarefas (Lógica de Comando, Monitoramento de Falhas, Controle de Navegação, Coletor de Dados). 
>
> **Na arquitetura atual do seu projeto:**
>
> * o **buffer circular compartilhado** já está implementado na classe `SharedCircularBuffer`, com:
>
>   * `write(const BufferData&, std::atomic<bool>&)`
>   * `read(size_t consumer_id, std::atomic<bool>&)`
>   * lógica de múltiplos consumidores via `m_consumer_read_heads` e predicados `is_full()` / `is_empty()`. 
> * existe um esqueleto de `tratamento_thread` que hoje:
>
>   * apenas gera valores fictícios (`data.i_posicao_x = 10; data.i_temperatura = 45;`)
>   * e escreve no buffer. 
>
> **Novo requisito:**
> Em vez de gerar dados fictícios, a tarefa Tratamento Sensores deve:
>
> * **assinar o tópico MQTT** `atr/mine/truck/001/sensors`;
> * **receber JSONs** como:
>
>   ```json
>   {
>     "truck_id": "001",
>     "timestamp": 1764540770.291139,
>     "sensors": {
>       "i_posicao_x": 1559,
>       "i_posicao_y": 370,
>       "i_angulo_x": 1,
>       "i_temperatura": 53,
>       "i_falha_eletrica": false,
>       "i_falha_hidraulica": false
>     }
>   }
>   ```
> * **parsear** esse JSON com **cJSON**, montar um `BufferData` coerente;
> * aplicar o **filtro de média móvel** onde for necessário;
> * e **escrever** no `SharedCircularBuffer` para as demais tarefas usarem.

## 2. Escopo da Tarefa (Tratamento Sensores)

> Você deve focar **apenas** na tarefa Tratamento Sensores e na sua integração com o `SharedCircularBuffer`.
> Não implemente aqui:
>
> * Lógica de Comando,
> * Monitoramento de Falhas,
> * Planejamento de Rota,
> * Controle de Navegação,
> * Coletor de Dados,
> * Interfaces gráficas / Python.

O escopo da tarefa inclui:

1. **Cliente MQTT em C++ (paho-mqttpp)**

   * Criar uma classe ou função que:

     * conecta ao broker (host/porta serão passados ou definidos em config);
     * assina o tópico `atr/mine/truck/001/sensors`;
     * recebe mensagens MQTT e entrega o payload JSON para o código de tratamento.

2. **Parsing de JSON com cJSON**

   * Ler o payload textual MQTT;
   * Usar **cJSON** para extrair:

     * `truck_id` (validar que é `"001"` ou generalizar para N caminhões se eu pedir);
     * `timestamp` (double ou equivalente);
     * os campos do objeto `"sensors"`:

       * `i_posicao_x`, `i_posicao_y`, `i_angulo_x`,
       * `i_temperatura`,
       * `i_falha_eletrica`, `i_falha_hidraulica`.
   * Tratar **erros de parsing** de maneira robusta (ignorar mensagens inválidas, logar erro, não travar a thread).

3. **Estrutura `BufferData` e filtro de média móvel**

   * Preencher uma instância de `BufferData` com:

     * os sinais lidos (`i_posicao_x`, etc.);
     * timestamp e/ou truck_id se a estrutura permitir (ou comentar se não existir campo).
   * Implementar o **filtro de média móvel** de ordem M (M definido em config ou constante):

     * manter um histórico das últimas M amostras por variável;
     * calcular a média e gravar no `BufferData` como **valor tratado**.
   * O objetivo é que os consumidores do buffer leiam **valores já filtrados**, em conformidade com o enunciado. 

4. **Integração com o `SharedCircularBuffer`**

   * Usar a API já existente:

     * `buffer.write(data, running_flag);`
   * Respeitar a lógica de bloqueio da classe:

     * o método `write` bloqueia se o buffer estiver cheio e libera quando consumidores avançarem; 
   * Garantir que a thread de tratamento:

     * use a flag `running_flag` para encerramento limpo;
     * chame `notify_all_for_shutdown()` (se adequado) ao encerrar o sistema.

5. **Thread de tratamento (`tratamento_thread`)**

   * Refatorar o esqueleto de `tratamento_thread` para:

     * **não gerar dados fictícios**;
     * acoplar com o loop de recebimento MQTT e/ou fila de mensagens;
     * controlar a política de espera (`sleep` / `wait`) de modo a:

       * não consumir CPU desnecessariamente;
       * não perder mensagens MQTT (usar callbacks/eventos).
