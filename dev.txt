## 1. Contexto e Reenquadramento

> **Onde o Coletor se encaixa no sistema:**
> No sistema de controle do caminhão autônomo, a tarefa **Coletor de Dados**:
>
> * lê o **estado do sistema** (sensores tratados, falhas, estados, setpoints) a partir do buffer compartilhado;
> * atribui um timestamp e registra em log persistente;
> * organiza os dados para posterior visualização/diagnóstico. 

No seu projeto, essa função é concretizada assim:

* O **SharedCircularBuffer** armazena **apenas uma estrutura única**, `BufferData`, contendo:

  * identificação (`truck_id`) e `timestamp`;
  * sensores tratados: `i_posicao_x`, `i_posicao_y`, `i_angulo_x`, `i_temperatura`;
  * falhas: `i_falha_eletrica`, `i_falha_hidraulica`;
  * estados: `e_defeito`, `e_automatico`;
  * setpoints: `setpoint_velocidade`, `setpoint_angulo`.

````cpp
struct BufferData
{
    std::string truck_id;
    double timestamp;
    int i_posicao_x;
    int i_posicao_y;
    int i_angulo_x;
    int i_temperatura;
    bool i_falha_eletrica;
    bool i_falha_hidraulica;
    bool e_defeito;
    bool e_automatico;
    double setpoint_velocidade;
    double setpoint_angulo;
    // construtor default...
};
``` :contentReference[oaicite:3]{index=3}  

- O **coletor** é uma thread do Processo 1 (núcleo embarcado), que deve chamar `buffer.read(ID_COLETOR, running_flag)` e persistir cada `BufferData` lido no InfluxDB.   
- O InfluxDB está acessível em:

  ```text
  INFLUX_HOST: http://influxdb3-core:8181
  INFLUX_DB: bms
  INFLUX_ORG: default
  INFLUX_TOKEN: "apiv3_..."
````

e você já possui uma classe `InfluxDBService` que encapsula as chamadas HTTP via libcurl (`connect()`, `insert()`, `insert_batch()`). 

**Objetivo desta tarefa:**
Implementar a thread `coletor_thread` em `coletor_de_dados.cpp` de forma que:

* consuma corretamente o `SharedCircularBuffer` usando o ID de consumidor do coletor;
* transforme cada `BufferData` em uma ou mais linhas no formato **InfluxDB Line Protocol**;
* envie de forma confiável para o InfluxDB (`InfluxDBService::insert` ou `insert_batch`);
* respeite o `running_flag` para desligamento limpo e o período `SLEEP_MS_COLETOR` configurado em `config.hpp`.

## 2. Escopo da Tarefa (Coletor de Dados)

> **Foque exclusivamente no Coletor de Dados e sua integração com:**
>
> * `SharedCircularBuffer` (leitura);
> * `BufferData` (estrutura única de amostra);
> * `InfluxDBService` (escrita).

Não implemente aqui:

* Tratamento de Sensores (MQTT/JSON);
* Lógica de Comando, Controle de Navegação, Monitoramento de Falhas;
* Interfaces gráficas;
* Simulação da Mina.

O escopo inclui:

1. **Leitura do Buffer Circular**

   * Usar `SharedCircularBuffer::read(size_t consumer_id, std::atomic<bool>& running)` com o ID do Coletor (`ID_COLETOR`).
   * Garantir que a thread não faz *busy-wait*: ela deve bloquear na `read()` até haver dados ou até `running_flag` ser desligado.

2. **Conversão `BufferData` → Influx Line Protocol**

   * Definir um *measurement* base, por exemplo: `"truck_state"` ou similar.
   * Usar tags e fields coerentes, por exemplo:

     * **Tag**: `truck_id`;
     * **Campos numéricos**: `i_posicao_x`, `i_posicao_y`, `i_angulo_x`, `i_temperatura`, `setpoint_velocidade`, `setpoint_angulo`;
     * **Campos booleanos**: `i_falha_eletrica`, `i_falha_hidraulica`, `e_defeito`, `e_automatico`;
     * **Timestamp**: derivado de `BufferData::timestamp` (em ns ou ms, conforme convenção do serviço). 

3. **Uso da API `InfluxDBService`**

   * Inicializar `InfluxDBService` com host, porta, token e database de acordo com as variáveis fornecidas (ou `config.hpp`).
   * Chamar `connect()` no início da thread (ou antes de entrar no laço principal).
   * Para cada `BufferData` (ou para lotes deles), chamar `insert()` ou `insert_batch()` com as linhas no formato correto. 

4. **Thread `coletor_thread`**

   * Assinatura típica (como já existe no esqueleto):

     ```cpp
     void coletor_thread(int id,
                         int sleep_ms,
                         std::atomic<bool> &running_flag,
                         SharedCircularBuffer &buffer);
     ```

   * Refatorar o esqueleto atual (que só loga “is running…”) para:

     * no laço:

       * ler `BufferData` do buffer;
       * montar linha(s) Influx;
       * enviar via `InfluxDBService`;
       * opcionalmente aguardar `sleep_ms` entre leituras (ou controlar taxa de flush).

5. **Robustez e desligamento limpo**

   * Utilizar `running_flag` para sair do laço;
   * Tratar exceções (de rede, Influx, etc.) sem derrubar o processo;
   * Garantir que a thread pode ser interrompida com `boost::thread::interrupt()` sem vazamento de recursos.
